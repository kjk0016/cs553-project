To an undergraduate computer science student about to build their first authenticated API, I would say try not to get overwhelmed. Instead I would recommend getting an understanding of some foundational concepts first. The first important step is understanding foundational concepts. Starting with the absolute basics, an understanding of the responsibilities between the client and server is an essential thing to know. The client is responsible for sending requests, while the server must validate the request, identify the user, enforce the permissions associated with that user, perform the requested task if allowed, and send a relevant response. 

Next, an understanding of HTTP is also essential. Having a strong understanding of how the protocol works, as well as the popular methods and status codes will help in the planning stage. Using common methods such as GET, POST, DELETE, etc…, will help define the routes the API will use. In addition to this, the popularity of the HTTP methods will allow clients to easily interface with the API. 

Another important thing to consider is the separation of routes, services, middleware, and database logic. In my design, I decided the route files should only determine which operation was requested and send the response, while the service files should handle the logic actually associated with the routes. Middleware was used for repeated actions such as requiring a certain role or validating a JWT. This was a design decision I made, not only because it was a project requirement, but also because it made updates easier to implement. Of course, like with any design decision, there were tradeoffs involved with this. Pros included making the files easier to read, maintain, and update, while cons included spending more time before implementation to think through exactly what belonged in each file. 

Database design, authentication, and authorization must be considered together because they all depend on each other. Authentication determines who is making a request. Authorization determines whether or not that user is allowed to make the request. The database supports both, as it stores user information needed for authentication and authorization, such as ids, password hashes, roles, and other information. It also contains the resources being requested. For example, a user might successfully authenticate with the API, but that doesn’t mean they should be allowed to delete every task. This is why it is important to consider all three together.

The most important technical concepts I learned were also what gave me the most difficulty in the beginning. These concepts being how authentication is actually implemented. I already knew how authentication worked conceptually, but it took me some time to understand the actual implementation such as creating login and register routes, hashing passwords, generating JWT’s, and validating those JWT’s.

One thing I would do differently if I were starting this project over, or beginning any new API project, would be to define who should have access to each route during the initial design phase. Before implementing a route, I would determine whether it should be available to anyone, only authenticated users, only administrators, or only the user who owns the resource. These access controls are something I did not even consider when I first started this project, but now recognize are important to determine in the planning stage to save time during implementation. 

Finally one security risk a development team should not overlook is actually validating the JWT. The JWT should not be accepted, just because the API can read it, and instead should be validated to make sure, that among other things, the digital signature is correct, the issuer is correct, and the token is not expired.
